# Go Search Trends

Сервис для отображения актуальных трендов поиска в реальном времени. Читает поток поисковых событий из Kafka и отдаёт топ-N самых популярных запросов за последние 5 минут.

---

## Быстрый запуск

**Требования:** Docker, Docker Compose.

```bash
git clone https://github.com/LeezyWannaFall/Go-Search-Trends.git
cd Go-Search-Trends
docker compose up --build
```

Сервис поднимается на `http://localhost:8080`.

---

## API

### GET /top

Возвращает топ-N самых популярных поисковых запросов за последние 5 минут.

**Параметры:**

| Параметр | Тип    | Описание                                  | По умолчанию |
|----------|--------|-------------------------------------------|--------------|
| `n`      | int    | Количество запросов в ответе              | 10           |

**Пример запроса:**

```bash
curl "http://localhost:8080/top?n=5"
```

**Пример ответа:**

```json
[
  {"query": "golang", "count": 42},
  {"query": "kafka", "count": 31},
  {"query": "docker", "count": 17}
]
```

При отсутствии данных за последние 5 минут возвращается `null`.

## Тестовая отправка событий

Подключиться к Kafka-продюсеру внутри контейнера:

```bash
docker compose exec kafka \
  kafka-console-producer --bootstrap-server localhost:9092 --topic search-events
```

Ввести событие в формате JSON и нажать Enter:

```json
{"query":"golang","user_id":"u1","timestamp":"2026-05-24T12:00:00+03:00"}
```

> ⚠️ Поле `timestamp` должно содержать **текущее время** — сервис хранит только данные за последние 5 минут. События с устаревшим временем будут получены, но не попадут в топ.

## Контракт данных

### Формат сообщения в Kafka (topic: `search-events`)

```json
{
  "query":     "golang",
  "user_id":   "user-42",
  "timestamp": "2026-05-24T12:00:00+03:00"
}
```

| Поле        | Тип              | Обязательное | Описание                                      |
|-------------|------------------|:------------:|-----------------------------------------------|
| `query`     | string           | ✅            | Текст поискового запроса                      |
| `user_id`   | string           | ✅            | Идентификатор пользователя                    |
| `timestamp` | string, RFC 3339 | ✅            | Время совершения поискового запроса           |

### Обоснование полей

**`query`** — основная единица данных. Именно по нему считается частота и строится топ.

**`user_id`** — нужен для будущей защиты от накрутки: позволяет детектировать аномальную активность одного пользователя (один `user_id` генерирует аномально большой поток одинаковых запросов). В текущей реализации поле принимается, но логика детектирования не реализована.

**`timestamp`** — время совершения поиска **на стороне продуцирующего сервиса**, не время получения события. Это принципиально: сервис строит скользящее окно по реальному времени поиска. Если использовать время получения (server-side), то задержки в Kafka или сетевые лаги исказят окно. RFC 3339 выбран как стандарт с поддержкой таймзон — это позволяет корректно принимать события из разных регионов.

## Архитектура и выбор структур данных

### Основное хранилище: `map[int64]map[string]int`

```
buckets = {
  29659854: {"golang": 12, "kafka": 5},  // минута N-2
  29659855: {"golang": 8,  "redis": 3},  // минута N-1
  29659856: {"golang": 4,  "docker": 7}, // минута N (текущая)
}
```

Ключ внешней map — `unix_timestamp / 60`, то есть номер минуты с начала эпохи. Это даёт уникальный ключ для каждой конкретной минуты за всё время.

**Почему не `[]bucket` (слайс)?** Слайс требует знать индекс нужной минуты или линейного поиска. Map даёт O(1) запись и O(1) доступ к бакету нужной минуты.

**Почему не heap/priority queue?** Heap ускоряет `GetTop`, но усложняет `Add` — каждый инкремент требует пересчёта позиции в куче. При соотношении записей и чтений 1:10–50 это не оправдано: проще пересортировать при чтении, чем поддерживать порядок при каждой записи.

**Почему не Redis Sorted Set?** Задача не требует персистентности — данные актуальны только 5 минут. Добавление Redis создаёт сетевую задержку на каждое чтение, что противоречит требованию "максимально быстро". In-memory решение даёт задержку в наносекундах.

### Конкурентный доступ: `sync.RWMutex`

По требованиям ТЗ чтений в 10–50 раз больше, чем записей. `RWMutex` позволяет любому количеству горутин читать одновременно — `GetTop` не блокирует другие `GetTop`. Только `Add` (запись) захватывает эксклюзивную блокировку.

### Стоп-лист: `map[string]struct{}`

`struct{}` не занимает памяти — это идиоматичный Go-способ реализовать множество. Проверка принадлежности — O(1).

## Trade-offs и решения по бизнес-логике

### Проблемы, выявленные в постановке

**1. «Последние 5 минут» — неточное определение**

Неясно: это ровно 300 секунд или 5 полных минутных окон? Решение: скользящее окно с минутной гранулярностью. Текущая минута + 4 предыдущих = 5 бакетов. Это чуть менее точно (±1 минута), но значительно проще в реализации и не требует хранения событий с точностью до секунды.

**2. Аномальные всплески — нет количественного определения**

ТЗ упоминает "конкурентов и парсеров", но не определяет порог. Без чёткого критерия любая реализация будет произвольной. Поле `user_id` в контракте заложено специально под будущую логику: можно добавить `map[string]map[string]int` (user → query → count) и отсекать запросы если один пользователь даёт >X% от общего объёма. В текущей реализации не реализовано.

**3. Время события vs. время получения**

Выбрано время события (`event.Timestamp`). Компромисс: если продуцирующий сервис отправляет события с задержкой или неправильными часами, они попадут в некорректный бакет. Альтернатива — использовать `time.Now()` на стороне консьюмера, но тогда теряется смысл поля `timestamp` и окно перестаёт отражать реальную картину поисков.

**4. Потеря данных при рестарте**

Все данные хранятся in-memory. При перезапуске сервис начинает с чистого состояния. Это соответствует требованию ТЗ («по умолчанию сервис не содержит никаких данных»). Компромисс: после рестарта топ пустой до тех пор, пока не накопятся новые события за 5 минут. Для виджета это приемлемо — кратковременная недоступность лучше, чем отображение устаревших данных.

**5. Стоп-лист статический**

В текущей реализации стоп-лист задаётся при инициализации и не меняется через API. Динамическое управление стоп-листом (`POST /stoplist`, `DELETE /stoplist/:word`) является следующим шагом.
